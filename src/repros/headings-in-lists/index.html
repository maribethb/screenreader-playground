Headings inside list items

Affected

We've confirmed VoiceOver on macOS with this page, in both Chrome and Safari. We haven't tried any other screenreader. We couldn't find anyone else reporting this, so it's possible it's specific to one VoiceOver setting (see the notes).

Steps to reproduce

In VoiceOver, "next heading" is VO+Command+H, or H if Quick Nav single-key navigation is on. In NVDA and JAWS it's H in browse mode.

  1. Jump to the "Repro" heading with the next heading key. This is the control: it shows that heading navigation works on this page.
  2. Press the next heading key again. The repro is a list of four items, and only the third one has a heading in it.
  3. Open the screenreader's list of headings (the rotor in VoiceOver, NVDA+F7 in NVDA, Insert+F6 in JAWS) and look for "This is a heading".
  4. Go back to the "Repro" heading and read forward one item at a time (VO+Right Arrow in VoiceOver, Down Arrow in NVDA and JAWS). The other three items are there to compare against: plain text, a paragraph and a button. If the heading is read differently from the others, or skipped, that's the bug.

Expected output

This is what the specs say should happen, not just what would be reasonable. The HTML spec lets an <li> contain any flow content, which includes headings. In ARIA, a listitem's children aren't presentational, and nothing restricts what can go inside one. So the heading is an ordinary heading, and the screenreader should treat it like any other heading on the page:

  • After "Repro", the next heading is "This is a heading", read as heading level 1. Some screenreaders will also say it's item 3 of 4 in a list.
  • "This is a heading" is in the headings list.
  • Reading forward item by item reads each item's text, with "This is a heading" read as a heading and "This is a button" read as a button, probably with the list's size at the start.

Actual output

With VoiceOver on macOS, in Chrome and Safari, H doesn't move to the heading inside the list. We haven't written down yet whether it skips it and goes on to "Notes", stops at "Repro", or does something else, or whether the heading is missing from the rotor too.

This isn't quite what happened in Blockly. Users pressed H in the flyout (the panel of items you can drag out) and nothing happened, but the flyout's labels were never real headings. Each label was a role="listitem" element whose aria-label ended in ", heading". The heading role couldn't go on the same element, because an element only has one role, and making it a heading would have stopped it being a list item. This page tests the obvious way out, nesting a real heading inside the list item, and whether that would have worked.

Notes

  • This isn't a spec problem, and the markup is a common pattern. A table of contents is a list of headings. Heydon Pickering's Inclusive Components recommends a list of cards with a heading in each one, so screenreader users get both heading navigation and an item count. If this page reproduces, it's a screenreader bug, not an authoring mistake.
  • There is a known way for headings to vanish, but it doesn't apply here. Some roles have presentational children, so a heading inside them stops being a heading. button, option and tab are the common ones, and WebKit has an open bug about headings inside buttons missing from the VoiceOver rotor. listitem isn't one of them.
  • VoiceOver on macOS exposes list items as groups. In VoiceOver's group navigation mode (VoiceOver Utility, Web), you have to interact with a list to get at its items, and in DOM navigation mode you don't. Our best guess is that heading navigation only fails in one of the two modes, so it's worth testing both and recording which one was on.
  • Safari drops list semantics from lists with list-style: none. This page keeps the bullets, so the list should be exposed as a list. If the bug only shows up without bullets, that's something else.
  • The heading is level 1 because that's the simplest version. It sits under the page's level 2 "Repro" heading, which is an odd outline but shouldn't affect navigation. If it turns out to matter, try level 3.
  • Blockly also put everything inside role="application" later on, which hands keys like H to the page instead of the screenreader. That would stop H working on its own, list or no list, so it's left out of this page. It landed about seven weeks after the issue was filed, so it wasn't the original cause either.
  • Blockly's flyout has since moved from list and listitem to listbox and option, for Windows Narrator. option has presentational children, so nesting a heading wouldn't work there even if this page shows that it works in a plain list.
  • Where the Blockly code came from: the markup at the time of the issue is in core/flyout_button.ts on blockly's add-screen-reader-support-experimental branch at commit 909c294e (5 January 2026), with blockly-keyboard-experimentation's add-screen-reader-support-experimental branch at 24edccbc (10 December 2025). Neither branch moved again before the issue was filed. The ", heading" label and the comment about roles are in packages/blockly/core/flyout_button.ts at 3c79e6cc on blockly's v13 branch (15 May 2026), which is where the H shortcut workaround was merged.

Sources

  • Blockly issue 9618 (March 2026): users expected H to move between flyout labels, and it didn't. The issue guesses that's because "they're not true headings" or because of the application role. A comment from micro:bit's user testing says users "do tend to try shortcuts they're used to".
  • Blockly pull request 9874: our workaround, which adds Blockly's own H and Shift+H shortcuts to move between labels in the flyout.
  • Blockly pull request 9774: added ", heading" to the end of the label's aria-label, with the comment explaining why it couldn't use the heading role.
  • Blockly issue 9495: the discussion of the flyout's ARIA structure. It started out proposing role="heading" for labels, and ended up with list items.
  • Blockly pull request 9747 (merged April 2026): added role="application".
  • HTML, the li element: the content model is flow content, which includes headings.
  • WAI-ARIA, listitem: no "Children Presentational" entry and no restriction on what it contains. Compare Children Presentational for the roles that do hide their children.
  • ARIA in HTML, li: an li inside a list can't take any role other than listitem, so <li role="heading"> isn't allowed. The heading has to be nested.
  • WebKit bug 244881 (filed September 2022, still open): headings inside a button aren't in the VoiceOver rotor, because button children are presentational.
  • Core-AAM, listitem: maps to AXGroup on macOS.
  • Apple's VoiceOver guide, navigating webpages: group navigation mode versus DOM navigation mode.
  • Scott O'Hara, "Lists and Safari": Safari drops list semantics from unstyled lists.
  • Heydon Pickering, Inclusive Components, "Cards" (2018): a list of cards with a heading in each.
