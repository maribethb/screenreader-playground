Live regions added with their text already in them aren't read

Affected

This is our best guess and nobody has confirmed it with this page yet. Blockly's own testing found that VoiceOver on macOS, NVDA and JAWS never read its notifications. ChromeVox did. The testing didn't record the browsers.

Steps to reproduce

  1. Jump to the "Repro" heading.
  2. Move to the "Show notification" button and press it.
  3. Wait until the screenreader has stopped talking, then press it again. Do this two or three times.
  4. Repeat all of this with the other variants.

Expected output

Each press reads "Notification 1", "Notification 2" and so on, in every variant.

The ARIA spec doesn't say whether a live region that arrives with its text already in it counts as a change, so this is what would be reasonable rather than what the spec requires. MDN's live regions guide says not to rely on it: set up the region empty, and change its text in a later task, or better, have the region in the page from the start. The two workaround variants do one each.

Actual output

Not confirmed with this page yet. In Blockly, at the commit that was tested, VoiceOver on macOS never read notifications, and we've checked that again in a Blockly checkout at that commit. NVDA and JAWS didn't either. ChromeVox did, but also read the notification's close button and the word "status". So we expect, in VoiceOver, NVDA and JAWS:

  • The new-region variant reads nothing.
  • The delayed-text and existing-region variants read every notification.

Variants

  • new-region
  • delayed-text
  • existing-region

Each notification is a new role="status" element, added to the page with its text already in it. This is the broken version, and what Blockly did when it was tested.

The same as new-region, but the element goes in empty and the text is added in a setTimeout(…, 0). This is what MDN suggests when a region has to be added on the fly, and what the Blockly testers tried first.

There's one role="status" element in the page from the start, and each notification changes its text. This is what Blockly does now.

Repro

Notes

  • This started out on a page about assertive live region messages being ignored, which isn't on the site any more. We couldn't get that page's symptom (an assertive message lost when focus moves) to happen outside Blockly, and the same testing said notifications were never read at all, so we tried those instead. Blockly's notifications were always polite, though, so whatever lost them probably had nothing to do with assertive, and they got their own page.
  • The new-region variant copies Blockly's notification ("toast") at the tested commit. To be more accurate, Blockly put the empty element in the page first and then set its role, its aria-live and its text, but all in the same task, so a screenreader probably can't tell the difference. aria-live="polite" is redundant on a role="status" element, but Blockly set both, so the page does too.
  • The page leaves out some things Blockly's notification had: a close button, removing itself after 5 seconds, a slide-in animation, and only showing each hint once per session. Blockly showed a notification when inserting a block from the toolbox, which also moved focus to the new block and set the text of a separate assertive live region, all at once. If the new-region variant is read fine here, those are the next things to add back, starting with the assertive message. a11ysupport.io's test data says VoiceOver on iOS lets an assertive message drop a polite one that's waiting, and that would be a different bug.
  • The delayed-text variant is close to the first approach in the Blockly issue, which added a new live region element for every message and set its text in a setTimeout(…, 0). The author said it "worked well for getting toast messages announced", but it was dropped because messages didn't interrupt each other, so the output fell behind while moving a block. That's a problem for a stream of messages, not for a notification on its own.
  • The existing-region variant is a simplified version of Blockly's fix. In Blockly, the notification is still a new element, but it's not a live region any more. Its text is sent through the live region Blockly already had for its other messages, which is offscreen. Here the visible notification is the live region, to keep the code short.

Sources

  • Blockly issue 9460 (November 2025): micro:bit's review of Blockly's live region announcements in VoiceOver, NVDA, JAWS and ChromeVox. This is where the result and the setTimeout approach come from.
  • Blockly's Toast.createDom, at the commit that was tested: how a notification was built. Notifications were polite unless the caller asked otherwise.
  • blockly-keyboard-experimentation's insertFromFlyout and the move hints, on its add-screen-reader-support-experimental branch as it was when Blockly was tested: inserting a block starts a move and then shows a hint as a notification, without asking for assertive.
  • Blockly pull request 9524 (closed December 2025 without merging): the first attempt at sending notifications through the shared live region.
  • Blockly pull request 9672 (April 2026): the fix that shipped, which takes the live region off the notification and announces its text through the shared one.
  • MDN's ARIA live regions guide: set up the region before changing its content, use a later task if the region is added with JavaScript, and prefer having it in the initial markup.
  • a11ysupport.io aria-live test data (tested November 2022): VoiceOver on iOS lets an assertive message drop a waiting polite one.
