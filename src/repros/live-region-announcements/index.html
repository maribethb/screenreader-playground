All repros

Repeated and overlapping live region announcements

Affected

We've confirmed VoiceOver on macOS with this page, in Safari and Chrome. NVDA and JAWS come from Blockly's own testing, which found that NVDA, JAWS and VoiceOver didn't read a message that was the same as the one before it, and ChromeVox did. That testing didn't record which browsers were used, except that one of the workarounds failed in NVDA with Chrome but not with Firefox.

Steps to reproduce

  1. Jump to the "Repro" heading.
  2. Move to the "Add item" button and press it three times. Wait for the announcement to finish each time, so the messages never have to interrupt each other.
  3. Move to the "Add item with tip" button and press it once. This adds an item and shows a tip at the same time, so there are two messages to announce at once.
  4. Press "Add item with tip" again, after the first one has finished.
  5. Repeat with the other variants. Switching variants reloads the page.

Expected output

The ARIA spec says screenreaders should present changes to a live region, but doesn't say what happens when the region is given the same text it already has, or when the text changes twice before the screenreader gets to it. So this is what would be reasonable, not what the spec requires:

  • Every press of "Add item" reads "Item added."
  • Every press of "Add item with tip" reads "Item added." and "Tip: new items go at the end of the list." Either order would be fine.

Actual output

With VoiceOver on macOS, naive was tried in both Safari and Chrome, and the rest in Safari:

  • naive: "Item added." is read after the first press of "Add item" and not after the next two. Setting textContent replaces the text node even if the text is the same, so the DOM does change, but the text doesn't, and that's what screenreaders seem to go by. "Add item with tip" only ever reads the tip, the same as one-region below.
  • one-region: every press of "Add item" is read. But "Add item with tip" only ever reads the tip, on both presses. "Item added." is never read, and it never shows up in the region on screen either, because it's replaced in the same click, before the browser draws anything or tells the screenreader about it.
  • new-element, two-regions, debounce and append: everything is read.

This is what Blockly's testing found with each approach, which covers the other screenreaders. The testing comment doesn't say which screenreaders every approach was tried with, but presumably it was all four.

  • naive: NVDA, JAWS and VoiceOver didn't read a message that was the same as the one before it. ChromeVox did.
  • new-element: repeated messages and both messages at once were read. The messages never interrupted each other, so pressing a button quickly got the screenreader further and further behind.
  • two-regions: repeated messages were read, and so were both messages at once. Again, the messages never interrupted each other.
  • one-region: repeated messages were read. With two messages at once, usually only one of them was read, and sometimes neither.
  • debounce: everything was read. This was the only approach that worked well in all four screenreaders.
  • append: everything was read, except in NVDA with Chrome, which read the whole region every time. So the second press of "Add item" read "Item added. Item added.", and by the end it was reading every message since the page loaded. NVDA with Firefox only read the new paragraph.

Repro

Notes

  • This page is about repeated messages, and about two messages arriving at once, which only came up because it decided between two of the workarounds. It doesn't try to compare polite and assertive regions. Live region messages set while moving focus aren't read has both. Every region here is polite. At the time of the testing, Blockly's region was assertive. It had been polite until a few days before.
  • It also doesn't cover messages overlapping with the screenreader's own output, like reading the newly focused element. Nothing here moves focus. That might end up as its own repro.
  • "Messages never interrupted each other" was a complaint about new-element and two-regions. Arguably that's just what a polite region is supposed to do, so it's not what this page is testing. That's why the steps say to wait between presses.
  • The non-breaking space trick relies on screenreaders not reading the non-breaking space, but still counting it as a change. one-region and two-regions compare against the last text that was set, so a third repeat drops the space again rather than adding a second one.
  • In one-region, step 4 sets the same final text as step 3. The tip is compared against "Item added.", which was set a moment earlier in the same click, so the tip doesn't get a space. We expected VoiceOver to skip it, the same way naive's repeated "Item added." is skipped. It didn't: it read the tip on every press. So replacing the text twice in one click counts as a change, even though the first replacement is never read, and setting the same text once doesn't. We don't know why. It also means this probably isn't where "sometimes neither" came from, at least in VoiceOver.
  • debounce alternates the space for every message, not for every announcement. "Add item with tip" sends two messages, so the space flips twice and ends up where it started, and the region's text is the same on every press. In theory that makes step 4 a repeat. But the region is emptied straight away and only filled 10 milliseconds later, and in VoiceOver that's enough: step 4 is read like any other press. Given what one-region does, the gap might not even matter, and any change in between might be enough.
  • In Blockly the tip was a toast, a visible popup that was its own live region. NVDA, JAWS and VoiceOver never read the toasts at all, probably because the toast's region was added to the page with its text already in it. That's a different problem, and it's why new-element sets the text a moment after adding the region. Here the tip is a plain message, so the page is only testing the two messages arriving at once.
  • The NVDA with Chrome problem in append looks like a bug in one of the two rather than anything to do with repeated messages. It might deserve its own page.
  • None of these shipped as-is. When the live region moved into Blockly core, it kept the debounce and the alternating space, but the latest message replaced any pending ones instead of being added to them, and the region was only emptied when the new text went in. That dropped messages, so a later change went back to collecting them, and then had to add punctuation between them so they didn't run together into one sentence. That history probably belongs in a separate repro about two messages at once, if we make one.
  • The code comes from microbit's experiments, which are on the aria-live-fixes and aria-live branches of microbit-matt-hillsdon/blockly, based on add-screen-reader-support-experimental at 74a36d77692de4e282fdffc4dfb4e7112f740edc. naive is announceDynamicAriaState in core/utils/aria.ts at that commit. new-element is 75ddf80c41240e33546a9589b1be83f45870d2e1, append is d1c7e55bb98802a3f851035c33bae5fe12442d07, and debounce is 05829f82107dfd1196866e3a8559791995cedb34. two-regions and one-region don't seem to have been committed anywhere, so they're written from the description in the testing comment. The comment says new-element used setTimeout(…, 0), but the commit uses 10 milliseconds, so that's what's here.
