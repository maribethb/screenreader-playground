Assertive live region announcements are ignored

Affected

This is our best guess and nobody has confirmed it with this page yet. Blockly's own testing found the bug in VoiceOver on macOS, but didn't record the browser. A WebKit bug reports VoiceOver on macOS skipping live region messages sent during a focus change in Safari, Chrome and Firefox, and Apple moved it to VoiceOver, so it's probably not browser-specific. The same Blockly testing found that ChromeVox, NVDA and JAWS all read the assertive announcement, so we expect those to work. Testing VoiceOver with both Safari and Chrome would tell us whether the browser matters.

Steps to reproduce

Reload the page between variants, so nothing is left in the screenreader's speech queue.

  1. Jump to the "Repro" heading.
  2. Move to the "Announce only" button and press it. This is the control: the live region changes and nothing else happens.
  3. Move to the "Insert block" button and press it. Focus moves to a new block, and the live region changes at the same time.
  4. Repeat both steps with the other variant.

Expected output

The ARIA spec says assertive updates should be presented immediately, and that a screenreader may clear its queue of pending speech to do it. Polite updates wait for the next graceful opportunity. So this is what the spec asks for:

  • "Announce only" reads "Announcement 1" in both variants.
  • "Insert block" in the assertive variant reads "Moving block 2. Use the arrow keys to move it." It may cut off the new block's name, or be followed by it.
  • "Insert block" in the polite variant reads the new block's name, then "Moving block 2. Use the arrow keys to move it."

Actual output

Not confirmed with this page yet. In Blockly, with VoiceOver on macOS, inserting a block from the toolbox moved focus to the new block and announced move mode in an assertive live region. VoiceOver read the block and never read the announcement. With the region set to polite, it read the block and then the announcement. So we expect:

  • "Announce only" works in both variants.
  • "Insert block" in the assertive variant reads the new block's name and nothing else.
  • "Insert block" in the polite variant works.

Variants

  • assertive: the live region has aria-live="assertive". This is the broken version.
  • polite: the same, with aria-live="polite". This is our workaround.

Repro

Notes

  • The title says "ignored", but probably that's not quite what happens. One guess from the Blockly testing was that VoiceOver starts reading the assertive message and the focus readout immediately cuts it off. The "Announce only" button is there to tell those apart: if it works and "Insert block" doesn't, assertive regions aren't ignored outright, they just lose to focus changes.
  • Some screenreaders have a milder version of this: they treat assertive as polite, so the message is read late rather than not at all. a11ysupport.io's test data records this for JAWS, Orca and TalkBack. This page won't show it, because there's nothing else queued for the assertive message to jump ahead of.
  • NVDA probably isn't affected, but it isn't a sure thing. An old NVDA issue reports a role="alert" message being lost when focus moved to a heading, and an NVDA developer explained that a focus change starts speech from a clean slate. Our own Blockly testing didn't see this with NVDA.
  • The repro moves focus first and then sets the live region's text. We don't know which order Blockly used. If this doesn't reproduce, it's worth trying the other order before deciding the bug is gone.
  • At the time of the testing, Blockly's live region was an offscreen <span aria-live="assertive"> that was always assertive. The region in the repro is visible, so sighted testers can see what should have been said. Today Blockly uses one polite role="status" region and switches its aria-live to assertive just before an assertive message, which is a different setup we haven't tested.
  • Every message is numbered, so it never repeats. Repeated messages are a separate problem with its own repro.

Sources

  • Blockly issue 9460 (November 2025): micro:bit's review of Blockly's live region announcements in VoiceOver, NVDA, JAWS and ChromeVox. This is where the VoiceOver result comes from.
  • Blockly issue 9632: the follow-up that made polite the default, because "some platforms wouldn't read assertive announcements at all".
  • Blockly pull request 9436: the change that made the region assertive in the first place.
  • WebKit bug 222190 (filed February 2021): VoiceOver on macOS skips live region messages during focus changes in Safari, Chrome and Firefox. Apple moved it to VoiceOver, and it still reproduced on macOS 13.1 beta in November 2022.
  • a11ysupport.io aria-live test data (tested November 2022): JAWS, Orca and TalkBack treat assertive as polite. VoiceOver on iOS lets an assertive message drop a queued polite one.
  • NVDA issue 11299 (2020, NVDA 2019.3 with Firefox): role="alert" not announced when focus moves at the same time.
  • JAWS standards-support issue 919 (September 2025): JAWS 2025 reads the newly focused field before an assertive message, where JAWS 2024 read the message first. Vispero confirmed it as a bug. The message is still read, just late.
  • WAI-ARIA 1.2, aria-live: what assertive and polite are supposed to do.
