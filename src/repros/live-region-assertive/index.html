Assertive live region announcements are ignored

This page is kept as historical context. The bug it was chasing turned out to be VoiceOver with Chrome losing live region messages set at the same time as a focus change, assertive or polite. That has its own page: Live region messages set while moving focus aren't read.

Affected

This is our best guess and nobody has confirmed it with this page yet. Blockly's own testing found the bug in VoiceOver on macOS, but didn't record the browser. That testing also found that ChromeVox, NVDA and JAWS all read the assertive announcements, so we expect those to work. A WebKit bug reports VoiceOver on macOS skipping live region messages during focus changes in Safari, Chrome and Firefox, which suggests the browser doesn't matter, but it doesn't say whether the region was polite or assertive. Testing VoiceOver with both Safari and Chrome would settle it.

Steps to reproduce

Reload the page between variants, so nothing is left in the screenreader's speech queue.

  1. Jump to the "Repro" heading.
  2. Move to the "Show shapes" button and press it. Three shapes appear, and focus moves to the first one.
  3. Press Enter on a shape. A copy of it is added to the canvas, the shapes are hidden, focus moves to the copy, and then the live region changes. VO-Space works too.
  4. Press "Show shapes" and add a copy two or three more times, waiting for the screenreader to stop talking each time.
  5. Repeat all of this with the other variant.

Expected output

The ARIA spec says assistive technologies should present assertive updates immediately, and polite ones at the next graceful opportunity. It calls this a strong suggestion rather than a requirement, and it doesn't say anything about how live regions should fit around the screenreader reading the focused element. So this is what would be reasonable, not what the spec requires: adding a copy reads its name, like "Red square 1, shape", and "Moving Red square 1". In the assertive variant the message may cut off the name. In the polite variant it comes after the name.

Actual output

Not confirmed with this page yet. In Blockly, with VoiceOver on macOS and an assertive live region, inserting a block from the toolbox read the new block's name and never the move announcement. With the region set to polite, the announcement was read after the name. So we expect, with VoiceOver:

  • In the assertive variant, adding a copy reads its name and nothing else.
  • In the polite variant, both are read.

Variants

  • assertive: the live region has aria-live="assertive". This is the broken version.
  • polite: the same, with aria-live="polite". This is our workaround.

Repro

Notes

  • The earlier versions of this page tried to reproduce the other case from the Blockly testing: starting a move on a block that already had focus. We never got that to fail. The first version set the text and then moved focus, and VoiceOver in Chrome and Safari started the message, was cut off by the focused element's name, and then read the message again from the start, in both variants. Switching to Blockly's order (focus first, then text), then to SVG shapes with role="figure" like Blockly's blocks, then adding the M key Blockly's testers pressed, and then wrapping everything in role="application", all behaved the same in both variants in Safari. In the last detailed run, assertive interrupted and polite waited, which is what the spec suggests, and the move message was never lost. Once, the first move on the page dropped everything after it, in both variants, and we never worked out why.
  • In Blockly, starting a move only lost the message some of the time, even in a checkout at the tested commit. Inserting from the toolbox lost it more reliably, so this version copies what happened to the page during an insert instead. The role="application" variants are gone, because Blockly didn't use it until pull request 9747 in April 2026, five months after the testing.
  • The shapes stand in for the toolbox's flyout, which was its own <svg> with a role="tree" group of role="treeitem" blocks. The canvas stands in for the workspace, a role="region" group of role="figure" blocks. Pressing Enter on a flyout block did all of this in one task: added a copy to the workspace, hid the whole flyout with display: none while one of its blocks still had focus, moved the copy into a separate drag layer, set the copy's aria-label, aria-selected and tabindex, focused it, and only then set the live region's text. The page does the same, apart from the drag layer. The copy goes straight into the canvas, because moving it to another group in the same task probably isn't something a screenreader can see.
  • aria-selected isn't allowed on role="figure", but Blockly set it, so the page does too.
  • Things Blockly did that the page leaves out, in case this doesn't reproduce. The toolbox's category list was an HTML tree, and its selected category was deselected in the same task. A notification was shown right after the announcement, which has its own page now (Live regions added with their text already in them aren't read). The announcement was longer and different every time, like "Moving to child of" followed by another block's whole label. Blockly only announced anything if there was already a block on the workspace to connect to, and it drew a connection preview and a move icon before the announcement.
  • Some screenreaders have a milder version of this: they treat assertive as polite, so the message is read late rather than not at all. a11ysupport.io's test data marks JAWS and Orca as doing this, and TalkBack's output in the same test looks the same. This page won't show it, because there's never a polite message queued for the assertive one to jump ahead of.
  • NVDA probably isn't affected, but it isn't a sure thing. An old NVDA issue reports a role="alert" message being lost when focus moved to a heading, though not when it moved to a button. An NVDA developer explained that a focus change starts speech from a clean slate. Our own Blockly testing didn't see this with NVDA.
  • At the time of the testing, Blockly's live region was an offscreen <span aria-live="assertive"> that was always assertive. The region in the repro is visible, so sighted testers can see what should have been said. Today Blockly uses one polite role="status" region and switches its aria-live to assertive just before an assertive message, which is a different setup we haven't tested.

Sources

  • Blockly issue 9460 (November 2025): micro:bit's review of Blockly's live region announcements in VoiceOver, NVDA, JAWS and ChromeVox. This is where the VoiceOver result comes from.
  • Blockly issue 9632: the follow-up asking for polite to be the default, because "some platforms wouldn't read assertive announcements at all". Pull request 9653 did it.
  • Blockly pull request 9436: the change that made the region assertive in the first place.
  • blockly-keyboard-experimentation's insertFromFlyout and startMove, on its add-screen-reader-support-experimental branch as it was when Blockly was tested: what pressing Enter on a flyout block did.
  • Blockly's Flyout.createBlock, at the commit that was tested: copies the block to the workspace and hides the flyout.
  • Blockly's BlockSvg.startDrag, LayerManager.moveToDragLayer, FocusManager.activelyFocusNode and BlockSvg.onNodeFocus, at the same commit: the copy is moved to the drag layer and focused, with its label and selection updated just before, and only then does startDrag set the live region's text.
  • Blockly pull request 9747 (April 2026): the change that put role="application" on the element Blockly injects.
  • WebKit bug 222190 (filed February 2021): VoiceOver on macOS skips live region messages during focus changes in Safari, Chrome and Firefox. Apple moved it to VoiceOver, and it still reproduced on macOS 13.1 beta in November 2022.
  • a11ysupport.io aria-live test data (tested November 2022): JAWS and Orca are marked as treating assertive as polite. VoiceOver on iOS lets an assertive message drop a queued polite one.
  • NVDA issue 11299 (2020, NVDA 2019.3 with Firefox): a role="alert" message lost when focus moved to a heading. It was closed in 2026 without a matching test case.
  • JAWS standards-support issue 919 (September 2025): JAWS 2025 reads the newly focused field before an assertive message, where JAWS 2024 read the message first. Vispero confirmed it as a bug. The message is still read, just late.
  • WAI-ARIA 1.2, aria-live: what assertive and polite are supposed to do.
