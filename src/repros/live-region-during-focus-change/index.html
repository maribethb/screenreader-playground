Live region messages set while moving focus aren't read

Affected

VoiceOver on macOS with Chrome. We tested with Chrome 155.0.8059.41 on macOS 27.0.1, and haven't recorded the VoiceOver version. VoiceOver with Safari isn't affected. We haven't tried Firefox, or any other screenreader with this page.

Steps to reproduce

Use Chrome, and reload the page between variants, so nothing is left in the screenreader's speech queue.

  1. Jump to the "Repro" heading.
  2. Move to the "Announce only" button and press it. This changes the live region without moving focus, to show that the region works.
  3. Move to the "Add item" button and press it. A new item is added, focus moves to it, and the live region changes.
  4. Move back to "Add item" and press it two or three more times, waiting for the screenreader to stop talking each time.
  5. Repeat all of this with the other variants.
  6. Repeat everything in Safari, which doesn't have the bug.

Expected output

"Announce only" reads "Announcement 1". Adding an item reads its name, like "Item 2: a button at the end of the list", and "Added item 2". The ARIA spec doesn't say how live region messages should fit around the screenreader reading the newly focused element, so this is what would be reasonable, not what the spec requires. An assertive message might cut off the name, and a polite one might wait until after it, but either way it should be read.

Actual output

In VoiceOver with Chrome, adding an item loses the message in the assertive, polite and text-first variants, and sometimes in set-timeout. group and div-with-id read it every time.

It only happens when the button you press and the new item have no container in common that Chrome puts in its accessibility tree, apart from the page itself. Chrome leaves a plain <div> out of the tree, but keeps it if it has an id, and it keeps any element with a role like group. So if "Add item" and the new item were both inside <div class="toolbar">, the message would be lost, and inside <div id="toolbar"> it would be read. Where the live region is doesn't matter. See the notes for how we found this, and how sure we are.

The details for each variant are in its tab, under "Variants".

Repro

Notes

  • Every repro on this site is rendered inside a <div id="repro">, and the id means Chrome keeps it in the accessibility tree. That would make it a container "Add item" and the new item share, and hide the bug, so on this page it has role="none". Keep that in mind if you copy the code onto another page: it only reproduces if nothing around it is in the tree.
  • This started out as the "Assertive live region announcements are ignored" page, which tried to reproduce what micro:bit's testing of Blockly found with VoiceOver: inserting a block from the toolbox moved focus to the new block and set an assertive live region, and the message was never read. With the region set to polite, it was read after the block's name. The first versions of that page were close to this one, with buttons standing in for blocks. VoiceOver read the message in both variants, so we decided we hadn't reproduced it, and spent several rounds copying more and more of Blockly onto the page.
  • The last of those rounds was a scratch page that copied every change Blockly made to the page when a block was inserted, in order, with a setting to turn each one off. It lost the message every time, in assertive and polite, even with almost everything turned off. Setting the text in a setTimeout, even with a 0 ms delay, got it read in both. Setting the text before moving focus instead of after, focusing an element that was already on the page instead of a new one, and changing the new element's label made no difference.
  • Then it turned out the browser mattered. Chrome lost the message on a copy of the earlier page, and Safari read it. In a Blockly checkout at the tested commit, Chrome never read the message, even with the region switched to polite, and Safari read it with the region assertive. We decided the earlier versions of the page must have been tested in Safari.
  • That was only part of it. When we moved the earlier page here, Chrome read the message every time, and over several sessions the same small page would read it, then lose it, then read it again. It came down to the wrapper around the repro. The copy that lost it had none, and this page had the <div id="repro">. Wrapping "Add item" and the new item in a plain <div> lost it, a <div> with an id or a role="group" got it read, and a <div role="presentation"> lost it. Wrapping only the live region, or only the new item, lost it too. It has to be something both of them are inside. The Blockly scratch page had a role="presentation" wrapper, copied from Blockly, so it lost the message too. To be more accurate about the earlier versions of the page, then: they ran inside #repro, so they probably read the message in Chrome as well, and the browser wasn't the whole story.
  • To check what Chrome does with each wrapper, we dumped its accessibility tree with tools/ax-ancestors.mjs. A <div> without an id is in the tree but marked ignored, one with an id is a generic node, a role="group" is a group node, and a role="presentation" one isn't there at all. Every page that read the message had a container the two shared that wasn't ignored, and every page that lost it didn't. That's Blink's tree, though, not the macOS one VoiceOver reads, and we haven't checked that with Accessibility Inspector yet. It's also possible the tree isn't the cause, just something that comes with it.
  • The set-timeout variant worked every time on the Blockly scratch page, but only some of the time here. Our guess is that a 0 ms timeout sometimes runs before Chrome has told VoiceOver about the focus change, so both still arrive together. We're testing longer delays.
  • This conflicts with the Blockly testing, which said polite was read after the block's name, and we can't explain it. The testing didn't record the browser. If it was Safari, assertive should have worked, and if it was Chrome, polite shouldn't have. It was almost a year before ours, so macOS, VoiceOver or Chrome might have changed since, but that's a guess.
  • The Blockly testing tried several fixes, and the one that "fixes the 'insert from flyout' problem" was a 10 ms debounce before setting the live region's text. They thought of it as stopping two messages from colliding, but it also moves the text into a later task than the focus change, which is what the set-timeout variant does. Blockly's live region has had a debounce since then, so Blockly is probably less affected now. Since a 0 ms delay isn't reliable, a 10 ms one might not be either. We haven't checked.
  • A WebKit bug reports VoiceOver on macOS skipping live region messages during focus changes in Safari, Chrome and Firefox. We only saw it in Chrome, and Safari read every message.
  • The Blockly testing found that NVDA, JAWS and ChromeVox all read the message when a block was inserted from the toolbox, so we don't expect them to be affected.
  • The Blockly checkout used core's add-screen-reader-support-experimental branch at 74a36d7 and blockly-keyboard-experimentation's add-screen-reader-support-experimental branch at a36f366.

Sources

  • Blockly issue 9460 (November 2025): micro:bit's review of Blockly's live region announcements in VoiceOver, NVDA, JAWS and ChromeVox. This is where the VoiceOver result and the debounce come from.
  • Blockly pull request 9436: the change that made the region assertive.
  • Blockly issue 9632 and pull request 9653: polite became the default, because "some platforms wouldn't read assertive announcements at all".
  • blockly-keyboard-experimentation's insertFromFlyout, on its add-screen-reader-support-experimental branch as it was when Blockly was tested, and Blockly's FocusManager.activelyFocusNode and BlockSvg.startDrag at the tested commit: pressing Enter on a block in the toolbox focused the new block and then set the live region's text, all in the same task.
  • WebKit bug 222190 (filed February 2021): VoiceOver on macOS skips live region messages during focus changes in Safari, Chrome and Firefox. Apple moved it to VoiceOver, and it still reproduced on macOS 13.1 beta in November 2022.
